# Деплой

Прод: **https://quiz.188-0-128-155.sslip.io**

Выкладка идёт **через GitHub**. Локального доступа к серверу в обычной работе не нужно:
запушили в `main` — через пару минут это на проде.

```
git push origin main
      │
      ▼
GitHub Actions (.github/workflows/deploy.yml)
      │  задание уезжает на self-hosted раннер
      ▼
quiz-vm (192.168.0.150)  ← раннер сам ходит наружу, входящих портов нет
      │  npm ci → tsc → vite build → scripts/ci-deploy.sh
      ▼
systemctl restart livequiz  →  health-check  →  проверка HTTPS снаружи
```

Смотреть ход и логи — вкладка **Actions** в репозитории. Там же кнопка «Re-run».

## Почему self-hosted раннер, а не ssh из Actions

Сервер живёт за NAT на приватном адресе `192.168.0.150`. Раннеры GitHub до него
не достучатся, а пробрасывать ssh наружу ради деплоя — лишняя дверь в интернет.
Self-hosted раннер устанавливает исходящее соединение сам, поэтому входящих портов
не нужно вовсе.

### ⚠️ Репозиторий публичный — что это значит

Self-hosted раннер в публичном репозитории опасен ровно одним сценарием: чужой форк
присылает PR, workflow запускается на вашем сервере и выполняет чужой код.

Поэтому в `deploy.yml` **нет и не должно быть `pull_request`**. Событие `push` в этом
репозитории может породить только тот, у кого есть право записи. Проверки для PR
вынесены в отдельный `check.yml`, и он крутится на одноразовых раннерах GitHub.

Если когда-нибудь понадобится запускать что-то на своём раннере по PR — сначала
сделайте репозиторий приватным.

## Что делает деплой

1. **Отказывается ломать живой вечер.** Перед выкладкой смотрит `/api/health`.
   Если хоть одна игра не в фазе `lobby` или `final` — вечер идёт прямо сейчас,
   и деплой отменяется: перезапуск оборвал бы вебсокеты у всего зала разом.
   Обойти можно вручную: Actions → Run workflow → `force = true`.
2. **Проверяет версию Node.** Сервер стартует как `node src/server/index.ts`,
   нативный TypeScript требует Node ≥ 22.18. Упасть здесь дешевле, чем после перезапуска.
3. Ставит зависимости, проверяет типы (`tsc --noEmit`), собирает клиент.
4. **Делает бэкап** текущего релиза в `/opt/livequiz-backups/previous.tar.gz`.
5. Раскладывает код в `/opt/livequiz` (без `var/` и `public/media/` — это данные,
   существующие только на сервере), ставит прод-зависимости, чинит права.
6. Перезапускает службу и ждёт `/api/health` до 20 секунд.
7. **Если не поднялось — откатывается** на предыдущий релиз автоматически.
8. Проверяет, что снаружи по HTTPS отдаётся 200.

## Права раннера

Деплой идёт от пользователя `ghrunner`, которому принадлежит `/opt/livequiz` —
поэтому почти всё делается без привилегий. Единственное, что ему разрешено через
sudo (`/etc/sudoers.d/livequiz-deploy`):

```
/usr/bin/systemctl restart|start|stop livequiz
```

Ни `/etc/shadow`, ни чужие службы ему недоступны.

## Ручная выкладка (запасной путь)

Если GitHub недоступен, с машины разработчика работает авторский скрипт:

```bash
scripts/deploy.sh azamat@192.168.0.150 /opt/livequiz
```

Он собирает клиент локально и увозит готовое по ssh.

## Секреты

`HOST_PIN` живёт в `/etc/livequiz.env` на сервере (права 600, владелец root) и в
репозиторий не попадает. Менять — на сервере, затем `sudo systemctl restart livequiz`.

## Куда смотреть, когда что-то не так

```bash
ssh azamat@192.168.0.150
sudo journalctl -u livequiz -n 50 --no-pager   # логи приложения
systemctl status livequiz nginx                # состояние служб
curl -s localhost:8787/api/health              # жив ли процесс
sudo journalctl -u 'actions.runner.*' -n 30    # логи самого раннера
```

Проверить прод снаружи (изнутри сети публичный адрес не открывается —
на роутере не работает hairpin NAT):

```bash
curl -s --resolve quiz.188-0-128-155.sslip.io:443:192.168.0.147 \
  https://quiz.188-0-128-155.sslip.io/api/health
```
